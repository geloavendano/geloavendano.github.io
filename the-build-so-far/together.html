House defaults: start here, then earn the exception

Defaults remove repeated decisions; they are not laws. Use the simplest option in the middle column unless the condition in the last column is true. Record every exception in a short decision record so the next session knows why it exists.

DecisionDefaultChange it when…
Content-only siteSemantic HTML + CSS + a little JavaScriptThe interface gains substantial shared state, authentication, or repeated interactive components
Interactive web appReact + Vite + TypeScriptYou need server-rendered pages, server actions, or route-level data loading; then use Next.js
Mobile appResponsive web first; Capacitor when native packaging is requiredThe product needs deep native capabilities or app-store UX that a web shell cannot provide
BackendOne dedicated Supabase project per product, plus a separate staging projectA written constraint makes isolation impossible; sharing quota, auth configuration, and blast radius must be explicit
Business rulesPure typed functions in a shared moduleThe rule needs secrets or authority; then enforce it on the server or in the database too
Multi-row writesOne database function or transactionThe operation truly has independent steps that may safely succeed separately
SecretsServer/edge function + host secret storeNever for a genuine secret. Browser variables are public, whatever their name

ObservabilityError tracking, useful structured logs, and 2–3 product events from the first sliceOnly a disposable prototype may omit it—and the omission gets a deletion date
Decision rule

Prefer the choice that makes the important rule easy to find, test, and enforce. Familiarity matters, but clarity at the trust boundary matters more.

Before the next build

The questions to answer before writing code — each one cheap to answer now and expensive to discover later. Distilled from the Barkhaus retrospective and this walkthrough; it grows as later deep-dives add lessons. The point isn’t to answer perfectly — some complexity only emerges — but the questions whose wrong answers are expensive to reverse (2, 3, 4, 6, 8) should get a deliberate answer up front, and whatever is most likely to grow should get a clean boundary around it. The answers feed step 1 of Day zero below.

  1. Scope & shape — what are we actually building?

    Draw the full flow for the most interactive feature — every step, every branch — not a one-line description. Count its distinct interactive states and its pieces of changing, shared state. Which parts are content (read once; must be fast and findable) versus a tool (used repeatedly by known users)?

    framework or plain files · one frontend or several · how much structure to impose on day one

  2. Surfaces & shared logic — who else will touch the same rules?

    List every surface, now and planned: public web, staff admin, mobile, partner API, internal scripts. Which business rules (pricing, eligibility, availability, permissions) does each one need?

    whether a shared business-logic module exists from commit one — if two or more surfaces share rules, it must. The single most expensive thing to retrofit.

  3. Data — what are the core things, and what do the fields mean?

    Name the 5–10 core entities and how they relate. Write the exact meaning of every date and status field (creation date vs event date; what each status means; which transitions are legal). What must never be lost, even when cancelled or deleted?

    prevents a whole class of “we each read this field differently” bugs — one page, one hour

  4. Trust boundary — what can’t the browser be trusted with?

    List everything a user could tamper with for gain: prices, totals, discounts, “am I allowed”, results, counts, “have I already done this”. What needs a secret key (payments, email, paid APIs)? What must all-succeed-or-all-fail together?

    which logic lives in server functions from the start — rather than added after an incident

  5. Environments — where do we test dangerous changes?

    Will there be a staging copy, or is it production-only? State it as a yes/no decision, not a default. How do we get realistic non-production data (a seed script)?

    makes the “we test schema and payment changes on live customer data” risk visible while it’s still a sentence

  6. Deploy & change pipeline — how does a change reach users?

    For each surface: is there a build step? Where does the built output go? Who deploys — a push, a bot, a person? How are database changes applied, and can they be rolled back?

    pick the host to fit the build strategy — instead of retrofitting (committed build output + a bot was Barkhaus’s most fragile part)

  7. Languages & types — how many, and typed?

    Can this be done in one or two languages (usually JavaScript/TypeScript + SQL)? What would force a third? TypeScript from the start — and types generated from the database schema?

    fewer languages = less to hire for and debug · types turn a bug class into editor warnings

  8. Build vs buy vs share — what are we not building, and where does it live?

    Which parts are solved problems to rent (database, auth, email, error tracking, hosting, payments)? What is genuinely ours and worth the time? And if we already run a project for another product — do we reuse it or stand up a fresh one?

    keeps effort on the product, not infrastructure · a shared project is faster to start but entangles quota, login config, and blast radius (MVL, Bonado and Sansayaw all share one Supabase project — hard to unpick later)

  9. Failure visibility — how do we find out when something breaks?

    Error tracking wired in from day one? Is any silent catch allowed, or must every failure surface? What is the one cheap integrity check that would catch data corruption early (e.g. bill total must equal the sum of line items)?

    a silent production failure should be impossible by default

  10. Team, lifespan & success — who maintains this, for how long, and how do we know it works?

    Solo, or rotating contributors and AI sessions? Weeks (throwaway) or years (load-bearing)? What one or two numbers say the product is doing its job, and what events do we capture from day one?

    more hands + longer life → more upfront structure, tests and docs · and you can tell whether the thing works

Plan the full stack, not only the feature

The ten questions define the product and its expensive decisions. The stack plan turns those answers into a complete operating system for the app. Go through all seven bands even when the answer is “not needed yet.” An empty slot otherwise defaults to something accidental—for example, no uptime check means customers become the monitoring system.

BandDecide before buildingEvidence before launch
01 · SurfacesPublic, admin, mobile, integrations; shared rules and supported devicesEvery surface completes the critical journey and uses the same authoritative rule
02 · StateDatabase, files, cache, search; ownership, retention, deletion, and invalidationConstraints and policies hold; realistic data stays queryable; stale copies refresh correctly
03 · Server logicTrusted handlers, transactions, jobs, queues; timeouts, retries, idempotencyDangerous inputs are rejected and repeated requests cannot duplicate important work
04 · DeliveryDomain, DNS, CDN, host, regions, TLS, app storesPreview, staging, production, redirects, certificates, and supported regions work
05 · Rented capabilitiesAuth, payments, email, maps, AI; secrets, sandboxes, quotas, fallback behaviorEach dependency has a tested success, failure, timeout, and cost/usage alert
06 · OperationsUptime, synthetic journeys, errors, logs, metrics, alerts, analytics, backupsAn outside check detects failure, a person receives it, and a restore has been rehearsed
07 · WorkflowGit, review, CI, environments, migrations, secrets, flags, release, rollbackA change follows the same safe path every time and production can return to a known state

Write scale assumptions before choosing scale tools

“Must scale” is too vague to design against. Write six numbers: daily active users, peak concurrent users, requests per minute, rows added per month, largest upload, and longest background job. Add a revisit trigger to each. This prevents both under-building and paying complexity tax for traffic that does not exist.

Two documents, two moments

  • Full-stack plan: design-time choices and assumptions. Fill it before the first vertical slice, then update it when a new capability enters the system.
  • Production readiness: proof-time checklist. Complete it before launch and repeat it before a major traffic or risk event.

Working templates: turn thinking into files

Open a template, edit it for the next project, then copy the result into that repository’s docs/ folder. Keep these notes short and update them with the code. Their job is to make assumptions visible—to you, collaborators, and whichever coding agent is helping.

How they connect: answer the ten questions once in Pre-build decisions. Then move the durable answers into the smaller documents that stay useful during delivery: app brief, data dictionary, Feature X-ray, decision records, and release checklist.

Challenge the idea before answering the questions

The notes above record decisions. Before making them, have Claude argue with the idea: question the request, think about growth, and compare with how similar products solve the same problem. Three pieces do this, and none of them build anything.

PieceKindIts job
architecture-challengeSkillAsks the hard questions in plain language, grounds each one in this portfolio’s lessons (“three products already share one Supabase project; does this one get its own?”), researches 2–4 comparable products, and writes the decision record
architecture-criticSubagent · read-only · can search the webReviews the draft cold: scale cliffs, choices that are hard to undo, trust and security gaps, blind spots, and over-building. Opens with Build as planned, Build after changes or Rethink first.
The triggerOne line in ~/.claude/CLAUDE.mdMakes sure the skill runs for every new app or major feature, without a hook firing on every small request
Plan modeBuilt into Claude CodeGuarantees nothing gets edited while you’re still deciding

Why not a hook? A hook runs a fixed command. It can’t reason about an idea, and it would fire on every small request (“fix this typo”) until you learned to ignore it. The decision record it produces has seven parts: the request and what’s out of scope, the recommended architecture with a diagram, alternatives considered, long-term risks, lessons applied, open questions, and the day-zero checklist. It lives in docs/decisions/, so every future chat can read why the app is built the way it is.

5 · Habits agreed before building

  • Every migration goes through rls-reviewer before you apply it, and to staging before production.
  • Anything touching payments, auth, RLS or personal data gets /security-review before it ships.
  • Test rounds use qa-pass, and qa-verifier checks the fixes before anything is called done.
  • “Shipped” means verified on the live URL (ship-and-verify), not pushed.
  • Docs change in the same commit as the code that makes them wrong: project instructions, handoff notes, the data dictionary.
  • Anything that runs on its own gets an alert, as a script where the check is a clear rule (see Scheduled runs).

Day one to launch: build vertical slices

A vertical slice is one small user journey that works all the way through the system: screen, validation, trusted logic, data, failure handling, and verification. It teaches more than building all screens first and connecting them later because every architectural assumption meets reality early.

01 · Define

Smallest useful journey

Name one user, one job, the successful outcome, and what is deliberately outside this slice.

02 · Draw

States and failures

Sketch empty, loading, ready, invalid, denied, failed, and successful states before polishing the happy path.

03 · Model

Data and ownership

Define the records, field meanings, legal transitions, owner, retention, and access policy.

04 · Bound

Trust boundary

Mark what the browser may suggest and what the server or database must decide and enforce.

05 · Build

One complete path

Wire the thinnest real journey through every layer. Avoid placeholder architecture that has never carried real data.

06 · Prove

Tests and evidence

Test the valuable rule and dangerous failure. Inspect the network, database, logs, and rendered result.

07 · Stage

Realistic rehearsal

Run the migration, seed realistic volume, exercise permissions and expected load, and verify rollback outside production.

08 · Observe

Make failure visible

Add error tracking, structured logs, uptime/synthetic checks, alerts, and the event that confirms the user outcome.

09 · Learn

One real user

Watch without coaching. Record where their mental model and the interface disagree.

10 · Expand

Next slice, same discipline

Add the next journey only after the first is understandable, protected, and observable.

11 · Release

Ship and verify

Pass production readiness, use the release checklist, deploy deliberately, and repeat the journey on the live URL.

12 · Reflect

Update the system

Write what surprised you, update decisions and instructions, and improve the house default.

Practice on the next feature

Stop after the first slice and teach it back

  1. Predict: before opening the code, sketch what should happen from click to stored result.
  2. Trace: find the event handler, rule owner, network call, database change, and visible result.
  3. Break: try an invalid value, a repeat request, no permission, and a failed dependency.
  4. Verify: name the evidence that proves each layer did what you think.
  5. Explain: write a five-sentence teach-back without copying the code.

Production readiness: prove the app can be operated

A release checklist asks whether one change is safe to ship. Production readiness asks whether the whole product can survive real users, real data, dependency failures, and an incident. Complete it before first launch, then repeat the relevant parts before a major event, payment launch, migration, or expected traffic spike.

Detect

Know it broke

External uptime, a synthetic critical journey, error tracking, missing-job detection, product completion events, and an alert that reaches a named person.

Withstand

Handle expected demand

Written scale assumptions, performance budgets, realistic data, load/spike/soak evidence, indexes, quotas, rate limits, and bounded retries.

Recover

Return to safety

Backups that include files, a rehearsed restore, RPO/RTO, rollback or forward-fix steps, feature flags, and a person authorized to act.

Protect

Keep trust

Authorization, least privilege, secrets, privacy, accessibility, compatibility, dependency review, and honest failure states.

Do not check boxes without evidence

Threshold

Replace “fast enough” with a number: p95 response time, page weight, job duration, or maximum error rate.

Artifact

Keep the test command/configuration, result, date, environment, and data size so the check is repeatable.

Owner

Name who receives the alert and who can disable, roll back, restore, or communicate.

Gap

If a check is intentionally deferred, record why, the risk accepted, and the date or usage trigger that makes it mandatory.

Use the editable production-readiness template. The underlying concepts—synthetic checks, load vs spike vs soak, quotas, idempotency, backups, RPO/RTO, and the incident loop—are explained in Part I.

Security baseline: automation plus judgment

Most security failures in this portfolio were either a leak (a key in the wrong place) or a design mistake (trusting the browser, RLS left off). They need different protection. Patterns catch known leaks; project rules and human review catch design mistakes. The implementation below is the existing Claude adapter. Repository-level secret scanning, tests and CI remain the cross-agent backstop.

Layer 1: automated guardLayer 2: project security rules
CatchesKeys in code, secrets shipped to the browser, .env read into the chat or committedBrowser-trusted prices, missing RLS, over-privileged functions, unneeded personal data
HowChecks every file read, write, edit and shell command before it runsRead at the start of every chat, in every project
ReliabilityEvery time, for known key formatsDepends on agent and human review, backed by tests and a security review
Fileclaude-setup/security/secrets-guard.pyclaude-setup/claude-md/global/CLAUDE.md

What the guard does

ResultWhen
BlockedWriting a private key; a Stripe, PayMongo, Supabase secret, Resend, GitHub, AWS, Anthropic, OpenAI or Slack key; a Supabase service_role key; or a database URL with a password into any file or command
BlockedA secret in a VITE_* or NEXT_PUBLIC_* variable, which ships to every visitor’s browser
BlockedOpening .env or key files (.p8, .pem) with the file reader; git add .env; git add -f; writing an env file that isn’t gitignored
Asks youA hard-coded password-like value, a Google API key (fine only if restricted), the service-role key named in browser code, cat .env, printing environment variables, editing an env file
AllowedThe Supabase anon key (public by design), placeholders, env(...) references, .env.example, and everything else

The Supabase anon and service_role keys look identical from outside. The guard tells them apart by reading the role written inside the key, which is how it can block one and allow the other. When it blocks, it tells Claude where the value belongs instead: a gitignored env file or the host’s secret settings, referenced by name.

Tested on this portfolio

  • 16 sample actions, all as expected: 6 blocked, 3 asked, 7 allowed, including a real-looking private key, an anon key (allowed), and Bonado’s PEM-parsing code (allowed).
  • Every tracked file in 8 repos scanned: no committed secrets. The first pass raised 9 false alarms (PEM-stripping code, env() placeholders, the word service_role in tests and docs, a minified library); the guard was tuned until all 8 came back clean.
  • All 5 existing .env files are gitignored and untracked.
  • Re-run any time without printing secrets: python3 claude-setup/security/secrets-guard.py --scan ~/Projects/<repo>

What the rules say

~/.claude/CLAUDE.md · the sections, abridged

# Security baseline (all projects)

## Secrets
- Keys live in gitignored env files or host secret settings, never in code, docs, commits, logs or chat.
- Only public values in VITE_* / NEXT_PUBLIC_* / browser code: the Supabase URL and anon key.

## The browser is untrusted
- Prices, totals, permissions, results are decided or re-checked on the server.
- Payment success comes from a verified webhook, never a redirect.

## Database access
- Every new table: RLS on, a policy per operation. Default to closed.
- SECURITY DEFINER functions set search_path, check auth.uid(), grant execute narrowly.

## Personal data
- Collect only what the feature needs. Admin = sign-in AND an allow-list row.

## Before shipping
- Payments, auth, RLS or personal data: run /security-review and say what it found.

Every rule traces back to something in Part II: the ₱1 checkout, RLS failing silently in Barkhaus, Sansayaw’s tables once writable by anyone, and the shared project.

Limits

  • Patterns catch known formats. A key in an unusual format, or pieced together from parts, gets through. The rules and /security-review cover what patterns can’t.
  • It guards Claude, not you. Your own edits and commits aren’t checked; GitHub secret scanning covers those.
  • Design mistakes still need review. No hook can tell whether a price should have been computed on the server. That’s what the rules, rls-reviewer and /security-review are for.

Turning it on

  1. Copy secrets-guard.py to ~/.claude/hooks/ and add its hooks block to ~/.claude/settings.json (the snippet is in claude-setup/security/).
  2. Copy the security rules to ~/.claude/CLAUDE.md.
  3. Turn on secret scanning and push protection for each GitHub repo.
  4. Open a new chat and ask Claude to read a .env file. It should be refused, with the reason.
