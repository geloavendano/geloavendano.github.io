Core principles

Before the projects: the vocabulary, and the handful of decisions that repeat across almost everything here. If the rest of the handbook assumes something, it’s probably explained in this section.

Words you’ll need

TermWhat it means
FrontendThe part that runs in the visitor’s browser or phone — what they see and click. Also called the client.
BackendThe part that runs on a computer you control — the database, and code that does things the visitor can’t be trusted to do. Also called the server.
Static siteA frontend that is just pre-written files (HTML/JS/CSS) handed to the browser as-is. No per-visitor work on the server. Cheap and fast.
SPA“Single-page app” — a frontend that loads once and then re-draws itself as you navigate, like a desktop program in a browser tab. Still just files to the host, but more of them and more complex.
FrameworkA pre-built foundation you write your app on top of (React, Next.js). Saves work; adds a build step and a learning curve.
Build stepA compile that turns source code into the files a browser actually runs. Frameworks need one; plain HTML/JS doesn’t.
RepoThe project’s folder under version control (git) — every change tracked, attributable, reversible. Lives on GitHub.
Host / deployThe host is the service that serves your site to the world (Vercel, GitHub Pages, Cloudflare). To deploy is to push a new version live.
MigrationOne written, ordered change to the database’s structure (a new table, a new column, a new rule). Applied deliberately, because it can’t be undone with a click.
Managed serviceInfrastructure you rent instead of run: Supabase (database), Resend (email), Sentry (error tracking). Someone else patches and scales it.

The trust boundary — and why it matters

Code runs in several contexts — the browser, a native shell, build and scheduled jobs, server functions, and the database. The security decision is simpler: code on the user’s device is untrusted; trusted backend code re-checks anything that affects money, permissions, inventory, or other people’s data.

Environments: local → staging → production

The same app is run in up to three settings, each with a different job.

Languages, and why these

LanguageUsed forWhy
JavaScript / TypeScriptBrowser code, Supabase Edge Functions, build toolingJavaScript is the browser’s main programming language, and the server functions run it too — so one language covers most of the stack. TypeScript is JavaScript plus static type information that catches shape mistakes before the code runs.
SQLEvery database — tables, access rules, and functions that run inside PostgresIt’s the language the database speaks; unavoidable, and often the safest place to put a rule (an access check or an all-or-nothing write).
PythonThe Sansayaw scrapers onlyBest-in-class ecosystem for “drive a browser, pull data, clean it.” Deliberately quarantined to the one job that benefits.
  • Speak the platform’s language. The browser runs JavaScript; the database runs SQL. Working against that grain costs more than it saves.
  • Fewer languages per project. Barkhaus, Bonado and MVL are essentially JavaScript + SQL and nothing else. Each language you drop is one less thing to learn, hire for, and debug.
  • Typed over untyped when it’s cheap. TypeScript keeps ordinary JavaScript syntax while adding types where they protect important shapes and contracts. Newer projects here lean this way; the older Barkhaus public site predates the habit.

The house stack — and when it strains

The four real products are all the same deliberate choice: a frontend that’s just files, one managed backend (Supabase), a static host (Vercel or GitHub Pages), and a few rented services for the specialist jobs (payments, email, error tracking). The diagram in The recurring pattern is this stack.

  • Great at: one or two people shipping fast; near-zero fixed cost; no servers to patch or scale. Each product can be fully isolated in its own project — though in this portfolio only Barkhaus is; the other three share one.
  • Strains when: you need heavy background processing, operations that must all-succeed-or-all-fail across several services at once, very high traffic on a tight latency budget, or you outgrow a vendor — moving off it is real work (“lock-in”).
  • Roads not taken: one large backend application (Rails / Django / Laravel) — more structure, one thing to deploy, but a server to run; a hand-built API (Node / Go) — total control, total maintenance; big-cloud serverless (AWS Lambda & friends) — endlessly flexible, and a part-time job to operate. At this portfolio’s scale the house stack is the right call — Barkhaus’s own retrospective says so in as many words.

Operating principles that repeat

  • Rent undifferentiated infrastructure; build only the product. Databases, logins, email, error tracking, hosting are solved problems. Effort goes into what’s actually yours.
  • Changes ship through git. Edit → commit → push → the host redeploys on its own. Every change is recorded, attributable, and reversible.
  • Database changes ride a separate, slower track. They don’t auto-deploy — each is a migration applied on purpose, because a bad one can’t be rolled back with a click.
  • Secrets never live in the repo. API keys sit in the host’s environment settings. Assume the repo is readable.
  • Feature flags keep things “built but dark.” Card checkout in Barkhaus is fully written and switched off by one setting — you can build ahead of launch without exposing it.

What each tool actually is

A common source of confusion is treating every named technology as the same kind of thing. They sit at different layers. React does not replace JavaScript; Vite does not replace React; Supabase does not replace Vercel. Each has a different job.

Quick classification

Predict

Explain

What happens when you click a button

Most application behavior is the same journey with different details. A user event changes local state, browser code may send an HTTP request, trusted code validates it, the database reads or writes rows, and a response redraws the screen.

1 · EventA click, submit, scan, timer, or app launch starts the work.
→
2 · HandlerA function reads the current inputs and decides what to do next.
→
3 · RequestThe client sends JSON to an API, RPC, or Edge Function.
→
4 · RuleTrusted code re-checks identity, permissions, totals, and invariants.
→
5 · StateThe database commits all valid writes or none of them.
→
6 · RenderThe response becomes success, failure, loading, or retry UI.

The same shape in code

browser → trusted server → database → browser

async function saveExpense(form) {
  setStatus('saving')                         // local UI state
  const response = await fetch('/expenses', { // HTTP request
    method: 'POST',
    body: JSON.stringify(form)
  })
  if (!response.ok) return setStatus('error') // failure is a real state
  const saved = await response.json()
  setExpenses(current => [...current, saved]) // render server truth
}

The names change between projects, but the questions do not: What starts the flow? What crosses the network? What is trusted? What persists? What proves success? The feature X-rays in Part II answer those questions with real files.

Five execution contexts

Client

Browser or web view. Great for interaction; readable and tamperable by the user.

Build / CI

Vite, Next.js builds, lint, type checks, and tests. Runs before users receive code.

Server / edge

Holds secrets, calls paid services, and validates requests.

Database

Stores durable state and enforces constraints, transactions, and row access.

Worker / schedule

Runs without a user watching: scrapes, cleanup, health checks, notifications.

Three views of the same app

A full stack is not a shopping list of technologies. It is one system viewed through three different stories. If you can tell all three stories, you understand the architecture well enough to change it.

Runtime

The request story

What happens from a user action to a visible answer? Follow the event, network request, trusted rule, data change, response, and rendered state.

Ownership

The truth story

Where does each fact live, and which layer has authority to change it? Separate display copies and caches from the source of truth.

Delivery

The change story

How does an edit become production behavior? Follow source, tests, build, configuration, migration, deployment, monitoring, and rollback.

One feature, seen three ways

ViewBarkhaus checkout exampleThe question it catches
RequestBooking form → checkout function → server repricing → Maya → verified webhook → confirmed bookingCan the browser fake the amount or the success result?
TruthThe browser holds an estimate; pricing tables and server computation own the amount; the webhook owns payment confirmationWhich copy is authoritative when two values disagree?
ChangePricing code and tests change → preview/staging checkout → function deploy → synthetic payment-health checkHow will we prove the new behavior reached production and stayed healthy?

Why all three matter

  • The request story finds broken flows. A button can render correctly while its request fails, or a request can succeed while the UI never reflects the result.
  • The truth story finds disagreement bugs. Barkhaus’s duplicated pricing and Sansayaw’s cache invalidation are both cases where two places could claim to know the same fact.
  • The change story finds operational gaps. Correct code is not a working feature until its migration, configuration, deployment, monitoring, and recovery path exist.

Explain one feature without brand names

Request

Describe the user action, trusted decision, stored result, and visible response.

Truth

Name the source of truth, any temporary copies, and what invalidates each cache.

Change

Name the tests, environment, deployment, live check, alert, and rollback.

Then tools

Only after the responsibilities are clear, name React, Supabase, Vercel, Sentry, or whichever products fill them.

Reading code without reading every line

Code is easier to understand when you identify its shape before its syntax. Start at the entry point, follow data, and stop when the behavior is explained.

The five-question scan

  1. What calls this function?
  2. What inputs can vary?
  3. Which branches change the outcome?
  4. What state does it read or change?
  5. How does failure travel back to the user or operator?

Where state lives

State is any fact the program must remember. Bugs often happen because the same fact is copied into two places and the copies disagree.

StateLifetimeGood forTypical failure
Local UI stateUntil the component/page closesOpen sheets, selected tabs, unsaved form valuesA refresh clears it.
URL stateShareable and survives refreshFilters, selected records, invite tokensSecrets placed in URLs leak through history and logs.
Session stateUntil sign-out or expiryWho the user is and their current access tokenIdentity is mistaken for authorization.
Server stateUntil the backend process or request endsValidated intermediate workServerless code assumes memory survives another request.
Database stateDurableBookings, expenses, classes, audit trailsTwo writers disagree or a partial write is committed.
CacheUntil expiry or invalidationAnswers that are expensive but safe to reuseStale data looks like truth.

A useful rule: keep the authoritative fact in one place, derive the display from it, and make cache expiry explicit. MVL’s duplicated league data and Barkhaus’s repeated pricing rules are examples of what happens when that rule is broken.

Debugging by evidence

Do not begin with “the app is broken.” Locate the first layer where expected and actual behavior diverge. Each layer leaves different evidence.

LayerEvidenceQuestion
UIExact steps, screenshot, visible stateDid the handler run, or is the problem before any request?
Browser codeConsole error and stack traceWhich function and source line failed first?
NetworkRequest URL, payload, status, response bodyDid the client send the intended data, and what did the server say?
ServerFunction logs and correlation/reference IDWhich validation, external call, or branch rejected it?
DatabaseRows, constraints, RLS policies, transaction resultWas nothing written, partly written, or written but hidden?
DeployCommit SHA, build log, live asset/versionIs the code being inspected actually the code users received?

The minimum useful bug report: exact reproduction steps, expected versus actual result, first error text, the network request/response when one exists, and the relevant record or schema shape with secrets removed.

The learning loop

Reading creates recognition; changing and verifying creates understanding. Use this six-step loop for every project lab.

01

Predict

State what you expect before running anything.

02

Trace

Follow the data from entry point to stored result.

03

Change

Make one safe, reversible local modification.

04

Break

Trigger one controlled failure and observe the evidence.

05

Verify

Use a test, query, log, or rendered result as proof.

06

Explain

Describe why the rule lives in that layer and what would fail if it moved.

The recurring pattern

Barkhaus, MVL, Sansayaw and Bonado are four takes on the same architecture. Rather than redraw it four times, here it is once. Each project’s deep-dive will describe how it bends this shape.

The stack map

The recurring pattern above is one way to fill in a working system. This is the whole menu. Every piece of working software has the same set of slots. What differs is who fills each one: you, a rented service, or nobody (and "nobody" still counts as an answer). The slots group into seven bands, and each band answers one question.

The irreducible minimum

Five slots can’t be skipped, even for a one-page brochure site: a surface (01), a host and a domain (04), version control (07), and some way to find out it broke (06). Everything else is switched on by something the product does. Use the table below as a completeness check, not a shopping list. Before building, go down the left column. Every “yes” adds the slots on the right, whether or not you plan for them.

Five scaling building blocks Recognize for later

The tables above list products. Underneath them sit a handful of general techniques that any system uses once it has to be fast, cheap, or survive traffic. You rarely buy these directly; they’re built into the products you rent. Each one exists to solve one specific problem.

ConceptThe problem it solves · its catchAlready in your stack asYou’d handle it yourself when
Object storageDatabases are slow and expensive at holding big files. A bucket stores each file cheaply and serves it from its own URL. The catch is bandwidth: downloads (“egress”) are billed.Supabase Storage: Barkhaus vaccine documents, Bonado receipts and trip covers.You serve a lot of video or large media, and download fees start to dominate the bill. Cloudflare R2 charges no egress.
CDNA server in one region is slow for users far away and buckles under spikes. A CDN keeps copies at “edge” locations near users, so the origin is asked only when a copy is missing or expired. The catch is serving an out-of-date copy.Vercel, GitHub Pages and Cloudflare all serve through one automatically. Sansayaw’s revalidate webhook is a CDN purge.You need to decide what may be cached, for how long, and how to force a refresh. Those are cache headers and purge rules.
CachingAnswering the same question over and over is wasted work. Keep the answer close. A hit answers instantly; a miss does the slow work once, then remembers it. The catch is invalidation: knowing when a saved answer is wrong.Sansayaw’s cached dataset; Bonado’s daily exchange-rate cache; Barkhaus loading pricing once at startup; plus every browser’s own cache.You can name the slow, repeated query. That’s when a Redis-style cache earns its place, along with a rule for when entries expire.
ServerlessAn always-on server costs money while idle. A function wakes per event and scales to zero. The catches: a cold start delay after idling, a time limit per run, and no memory between runs.Every Supabase Edge Function across the portfolio; Sansayaw’s Next.js server code on Vercel.Jobs run past the time limit, you need a connection that stays open, or traffic is steady enough that an always-on server is cheaper.
Load balancingOne server has a ceiling and is a single point of failure. A load balancer spreads requests across several servers and skips any that fail a health check. The catch: servers must be stateless, so nothing important can live in one server’s memory.Invisible. Vercel, Supabase and Cloudflare balance traffic for you. No project here runs its own.You run your own long-running servers (band 03). Then you need two or more instances, health checks, and sessions stored outside the server.
  • They line up along one request. A user’s request hits the CDN edge first. If it isn’t served there, it passes a load balancer to a server or a serverless function. That code checks a cache before asking the database, and big files come from object storage. Every layer is there to stop the request from traveling any further than it must.
  • The house stack rents all five. That’s why none of them show up in the deep-dives: they’re real, just invisible. It’s the managed-service trade in action: you give up control of these layers and never have to run them.
  • Caching is the one you still own. The other four are handled by the vendor. Deciding when a cached answer is stale is always your call, which is why Sansayaw’s revalidate webhook and Bonado’s per-day rate snapshot are both deliberate design decisions.

Bundled vs. assembled

The biggest choice on the map isn’t any single slot. It’s how many slots one vendor fills for you.

What isn’t a slot

  • Security is a property of every band, not a band of its own. Split into concrete pieces, it’s secrets (07), access rules and the trust boundary (02, 03), edge protection and rate limiting (04), dependency updates (07), backups (06), and how accounts and projects are separated (the whole map). Whatever is left under the “cybersecurity” label is usually a policy question, not something you buy.
  • Cost works the same way. Every band has a free tier and a point where the price jumps. The ones to watch are billed per event: email volume, map lookups, AI calls, analytics events.
  • An empty slot is still filled. With no error tracking, the slot is filled by “a customer tells you.” With no staging, it’s filled by “production.” Choose deliberately rather than by default.
  • Three slots get expensive if filled late: migrations, a shared business-logic module, and error tracking. All three appear in the Barkhaus retrospective.

This map is the menu. Before the next build is the set of questions that picks from it.

Reliability, capacity, and recovery

Building the feature answers: does it work? Operating the product adds four harder questions: is it working now, will it survive expected demand, what happens when a dependency fails, and how do we recover? These are part of the stack, not polish added after launch.

Five signals that answer different questions

SignalWhat it tells youWhat it missesUseful first version
Uptime checkCan an outside machine reach a URL on schedule?A homepage can be up while checkout or sign-in is broken.Check the public URL every 5 minutes from outside the host.
Synthetic journeyCan a robot complete a critical user flow?It covers chosen flows, not every real-user path.Sign in to a test account, read a known record, and stop before destructive actions.
Error trackingWhich exceptions users actually hit, in which release and code path?Slow success and wrong-but-valid data may raise no exception.Capture browser and server errors with release version and safe context.
Logs and metricsWhat the system did and how often: latency, failures, queue depth, job duration.Raw logs do nothing unless someone can query them and an alert uses them.Structured logs for critical actions plus success/error counts and duration.
Product signalWhether the user outcome happened: booking confirmed, expense saved, class found.A completed event does not prove every technical component is healthy.Track two or three completion events and their failure rate.

Health check vs uptime check: a health endpoint says one component can answer right now; an uptime check is the outside service that calls it repeatedly and alerts someone. A useful health check tests the dependency needed for the journey, not merely that the process started.

Volume is several tests, not one

TestQuestionExamplePass condition
PerformanceIs one normal request fast enough?Load the booking calendar with a realistic month of rows.A written threshold such as p95 under 800 ms, not “feels fast.”
LoadDoes expected concurrent traffic still meet that threshold?Simulate the users expected during an MVL raffle opening.Error rate, latency, and database connections stay inside limits.
SpikeWhat happens when traffic jumps suddenly?A link is posted and 10× normal users arrive in one minute.The system queues, rejects, or slows predictably instead of corrupting data.
SoakDoes ordinary load cause leaks or buildup over hours?Run repeated reads and background jobs long enough to expose connection or queue growth.Memory, connections, retries, and pending work return to normal.
Data-volumeDoes behavior stay correct with months or years of rows and files?Search, paginate, export, and enforce policies against a seeded large dataset.Queries use indexes, pages stay bounded, and jobs finish before their limits.

Begin with an explicit assumption, not a giant test: daily active users, peak concurrent users, requests per minute, rows added per month, largest upload, and longest job. Test the expected peak first, then a modest safety margin. Run destructive volume tests in staging with generated data, never casually against customer production.

Limits, overload, and graceful failure

  • Every rented service has quotas. Database connections, function duration, email sends, map calls, storage, bandwidth, and API rate limits all have a ceiling. Record the ceiling and alert before it becomes an outage.
  • Rate limiting protects both reliability and cost. Limit by authenticated user or safe client identifier, return a clear retry response, and put stricter limits on expensive or abuse-prone operations.
  • Retries need idempotency. A timeout does not prove the first request failed. Repeating a payment or multi-row write must not duplicate it.
  • Backpressure is an honest “not yet.” A queue, bounded batch, or temporary rejection is safer than accepting unlimited work the system cannot finish.
  • Dependencies need timeouts and a fallback. Decide whether the user retries, sees cached data, continues without the optional service, or is stopped safely.

Backup is not recovery

TermPlain meaningDecision to write down
BackupA separate recoverable copy of data.What is covered, how often, how long retained, and whether files are included.
Restore testProof that a backup can become a working system.Who restores it, into which environment, and how correctness is checked.
RPORecovery point objective: how much recent data you can afford to lose.If RPO is one hour, the backup or replication interval must support it.
RTORecovery time objective: how long the product may remain unavailable.If RTO is four hours, ownership and restore steps must make that realistic.
RollbackReturn application code or configuration to a known good version.Database migrations often need a forward fix because deleting new data may be unsafe.
