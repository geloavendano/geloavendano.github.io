The landscape

The application repositories and their working copies in ~/Projects collapse into five groups — four real products and a bag of demos. Two folders are noise: mvl-vercel-upload.zip (a stale export) and Sponsor Logos/ (just image files).

The through-line: almost every product is a frontend served from a static host, talking to a Supabase backend for data, accounts and files, with a few outside services bolted on for payments, email and maps. Learn that one shape and you understand 80% of everything here. Only Barkhaus has a dedicated Supabase project; Sansayaw, MVL and Bonado share one.

A Barkhaus Live

In one line

A booking platform for a two-branch pet-care business (Estancia & Eastwood, at barkhaus.ph) covering daycare, overnight hotel, and grooming — with a staff admin console behind it. It is the most built-out project here and the only one taking real money from real customers.

Architecture

It follows the recurring pattern with one twist: two separate frontends share one Supabase backend. The public site is plain hand-written HTML and JavaScript (no framework compilation). The committed Cloudflare Pages build copies selected files into dist/; the 27 Oct release report records the hosting cutover. The admin app is React and has to be compiled; the compiled result is committed into the repo and served alongside the site. Everything sensitive — payments, email, confirming a booking — runs in Supabase Edge Functions where the secret keys live.

Data model — the shape

bookings is the hub, but it does not hold the appointment date. That lives in a per-service detail table (grooming_details, hotel_details, …) as service_date. The booking_date column on the booking row is the date it was created — a naming trap that has broken the calendar, availability, and check-in code independently.

Key flows

A booking is born three ways

Online — the customer completes the wizard and pays on a hosted page; the checkout function first writes pending bookings and inventory holds; the payment webhook confirms them and sends email. An order can group several bookings into one hosted payment. Admin — staff use a 6-step panel; the submit-booking function writes it directly and emails immediately. Walk-in — staff mint a single-use token that opens the public wizard in a fee-free mode, also routed through submit-booking.

Keep checkout identity and service identity separate

browser cart → server validates one customer + one branch
  → price each item; charge the convenience fee once
  → pending booking + detail + inventory hold for each item
  → booking_orders + one hosted payment
  → verified webhook amount = order amount
  → finalize each booking; allocate its share to payments
browser return → query server status (the URL proves no payment)

Uniqueness must match the business event. One provider payment ID now legitimately occurs on several booking payment rows. The migration changes uniqueness to (reference_number, booking_id), retaining duplicate protection per booking. Nullable order links preserve legacy/admin/walk-in rows. The order reference starts from the first booking; multi-item booking references receive letter suffixes in checkout code, despite the migration comment describing the older unsuffixed behavior. Read current writes as well as schema comments.

A lock belongs to an order, but validation belongs to every item. 03f4bf9 reuses an already acquired inventory key/token inside the request. Previously two different hotel rooms shared a branch-wide lock and the second item conflicted with its own order. Each item still checks availability and hotel blocks; another order must acquire its own lock. The lock request has a 120-second lifetime, so slow work and expiry still need integration tests. Cleanup is compensating code across requests, with swallowed cleanup errors, not an atomic transaction.

Paid is not the same as fully reconciled. The webhook checks the total, claims the order by changing pending to paid, then finalizes bookings individually. The claim gates email; it does not wrap all writes in a database transaction. In finalizePending, a payment-row insert error is logged, yet the pending row is subsequently deleted. A green order status therefore cannot prove that every allocation exists. Reconciliation must compare the provider amount, order total, child statuses and payment sums, and test failures between these writes.

Recover the whole intent after leaving the page

9231be7 saves the full cart payload, current editable item, order summary and cancellation capability into the return snapshot before redirecting. Retry cancels the previous attempt and replaces references/tokens with the new checkout response; Edit restores the current item, including vaccine choices fixed by f8b2854. The return screen says Order total until payment is established. Session storage can fail or be lost; it is recovery context, never payment authority.

The different-pet change ends by removing a second browser-side save: checkout already upserts the pet under its owner by case-insensitive name, before payment. That avoids two writers with different deduplication rules. It also means a newly visible pet is not evidence of payment, and same-name pets need an explicit identity policy.

Verify & carry forward

Use fixtures for two rooms sharing a mutex, duplicate inventory, a competing cart, failed payment-row insertion, lost return storage, retry/edit and old single-item holds. In an isolated backend, verify anonymous/customer/staff view access and interrupted settlement. In a controlled release, reconcile a real multi-item payment before treating the cart as operationally proven. Make the release gate cover the full new cardinality.

Risks & gotchas

  • Staging simulation has a narrower proof. The committed non-production checkout path uses a payment simulator. It can exercise order state without moving money, but cannot prove the production provider, webhook delivery or real settlement. See the release gates.
  • Database changes are applied by hand. Each schema change is a SQL file a person runs against the live database, then a cache-reload command. Forget the reload and the API throws phantom “relationship not found” errors. There is no automated migration runner.
  • The admin app is a built bundle committed to the repo — and a bot also commits it. This has raced a real fix and reverted it (“the regression that kept coming back”). The documented fix — build in CI, stop committing output — is agreed but not yet done.
  • Row-level security has failed silently. An insert-only policy let edits add new charge lines while deletes quietly failed → duplicated bills (real money data), caught only by a test’s totals check. Public availability had to move to narrow server-side functions because a normal query returned “no bookings” — making every slot look free — when the booking rows were private.
  • The same business logic lives in three places. Pricing and availability rules are re-implemented in the public site, the admin app, and the test suite, and they have drifted (hotel priced by pet size in one, by cage type in another).
  • Payment health needs an outside watchdog. A GitHub Action pings a health function every 20 minutes, because a silently-failing cron — or a Supabase usage cap that stops functions responding — would not otherwise be noticed.
  • The docs already disagree with the code. AGENTS.md and the technical doc still say “manual transfer is active, keep Maya off until launch” — but the live setting is 'maya' and card checkout is running. Documentation that isn’t updated with the change that invalidates it quietly turns into a trap.

If we rebuilt it

Mostly straight from the team’s own retrospective — the stack was judged right; the discipline around change is what it would upgrade.

  • Contracts first. Schema in migrations from commit one, generated types, one shared business-logic module every surface imports, and a one-page data dictionary that pins down date semantics.
  • Two environments. Production plus a staging Supabase with a seed script, so destructive testing never touches live data.
  • CI builds artifacts. Never commit build output; remove the bot’s write path entirely.
  • Loud failures from day one. No silent catch {}; error tracking (Sentry) on both frontends — which Bonado already does.
  • Keep what worked. Database-driven pricing, the idempotent-webhook + pending-hold + auto-cancel trio, single-use tokens, soft deletes, and the cached-token auth pattern all earned their place.

The game-day raffle check-in — the signature flow

Two ways in: self (your own phone) or QR (a booth laptop where staff are signed in as admin). Either way the browser reads your location once — no manual pin — and hands it to one server function, which decides everything.

The site changes shape between “registration” and “game day” by editing one word in site-config.js. That swaps every page’s navigation (Rules/Waiver → Schedule/Videos/Teams/Rules/Check-In). Feature X-ray · feedback word clouds without losing context

Learning objective: trace a derived visualization back to its measurement and trust boundary. 6547967 adds a browser-generated word cloud above each written-response list. It adds no database field, analytics service, or visualization dependency.

Source trail
mvl/js/admin.js: loadFeedbackSummary → RPC mvl_admin_feedback_summary → feedbackQuestionCard → feedbackWordCloud.
supabase/migrations/20260908000200_feedback_report.sql establishes the admin check and report shape; later feedback migrations evolve it. mvl/css/style.css renders the wrapping word list.

The browser already receives the written answers through the admin report. The new helper lowercases text, tokenizes Unicode letters/numbers, removes short words, numeric-only tokens and English/Filipino stop words, then counts occurrences in a Map. It sorts by frequency with an alphabetical tie-break, keeps at most 36 terms, and uses a square-root scale for font size. When at least six distinct terms repeat, singleton terms disappear; with fewer repeated terms, singletons remain eligible. Equal counts receive one common size. Labels expose the exact count, while original answers remain below the cloud.

Frequency is not respondent count or sentiment. One answer containing “parking parking parking” contributes three mentions. Removing “not” or “hindi” discards negation; a large “good” could come from negative sentences. The six-term threshold also changes what is visible as data grows. Keep raw context and the counting rule available, and do not interpret size as the percentage of participants who agree.

Authorization and escaping do different jobs. The server RPC checks admin access; hiding the page would not protect its response. The cloud escapes both displayed tokens and title/ARIA labels, and the answer list escapes full responses before HTML insertion. This prevents text from becoming markup; it does not anonymize a report or make it safe to publish.

Verify with invented answers

Test repeated words within one answer, punctuation, apostrophes, Filipino/English stop words, equal frequencies, empty input, the five-to-six repeated-term transition, and a markup-shaped string. Confirm accessible labels preserve counts and the original escaped answer is still available. Do not use participant data as a test fixture.

Carry forward

A summary should reveal its unit, filters, and omissions. Keep the underlying evidence alongside it; an attractive visualization cannot supply missing meaning.

Risks & gotchas

  • The “one project per product” rule is broken here. MVL, Bonado, and Sansayaw all run inside one Supabase project (each in its own schema). Consequences: a redirect-list slip sends MVL’s admin login to Bonado’s site; Sansayaw’s daily scrapes and MVL’s game-day traffic share one quota; a migration mistake touches a database two other live products depend on. And this repo can’t use standard migration tooling — every schema change is run by hand against the live shared database.
  • The docs are badly out of date. HANDOFF.md still describes July: “raffle BUILT, pending one migration,” “remaining: team detail pages,” “phase deliberately not flipped.” Reality: the tournament ran, ~67 migrations landed, the phase is flipped, and there’s award voting, player check-ins, a raffle-draw system, a synchronized public draw display, and a feedback form. Same disease as the Barkhaus payment docs.
  • Two sources of truth for league data. js/league-data.js (teams, games, sponsors) was the original data source and is still used to render parts of the site, even though the same data lives in Supabase. The schedule page re-implements the standings ranking in JavaScript “until the page is wired to Supabase.” They can disagree.
  • Raffle rules changed ~10 times mid-event. Repeat winners, exclude-winner-dates, exclude teams, roster QR entries… the client re-decided eligibility game by game. This only worked because the logic was one server-side function to edit — a browser implementation would have needed a redeploy each time and drifted between the check-in page and the draw.
  • Scorekeeping by secret link. The scoreboard control URL is a bearer token — whoever has the link can score the match. Fine for a trusted volunteer on the day; it would need real accounts at any larger scale.
  • A hardcoded venue ID. The whole check-in flow depends on a magic UUID (11111111-…) pasted into the frontend. That venue row was once seeded with an empty location, which silently failed every check-in until a migration set the real coordinates.
  • Changes went straight to a production database during a live event. Raffle-rule migrations carried the note “get client go-ahead before applying — it’s their production DB.” There is no staging copy.

If we rebuilt it

  • Its own Supabase project. A free six-week event doesn’t justify entangling three products’ Auth, quota, and migration history. A new project costs nothing; unpicking this later is real work.
  • One data source. Once the pages read Supabase, retire league-data.js as a runtime source — keep it only as a seed file.
  • Keep the function-per-write discipline. It’s exactly what made the mid-event rule churn survivable. This is the pattern to carry forward, not fix.
  • Keep the one-word phase flip and the nav-sync check. Small, cheap, and it held up.
  • A staging copy. Same gap as Barkhaus — rule changes shouldn’t go straight to the live database mid-tournament.
  • Real accounts for scorekeepers if the event grows; the secret-link approach is an event-day expedient.

Data model — the shape

The core tables live in the sansayaw schema. classes preserves each scrape observation; class_records reconciles those observations into enduring identities, with aliases and events. Each snapshot row points to its scrape run, studio, and first-billed instructor when resolved. class_instructors holds the full ordered roster, including collaboration partners. The private instructor_aliases table turns scraped names into identities. The optional classes.booking_url carries a registration destination that may be shared by an entire branch through classes_display. portal_classes, ordered portal instructors, rooms and series now supply managed schedules; the combined v2 view joins those with reconciled scrape records, and classes_schedule_v1 adds instructor links for web and mobile. Private registrations, contact settings and delivery queues are separate from that public projection. The independent promos table carries active editorial slides; it does not point to a scrape run, and is outside the class-identity diagram below.

Key flows

The daily pipeline

The cron fires → the runner reads portal-managed studio IDs (failure stops the run) → the scraper opens a run record → each studio scraper pulls its data (a real browser for only 3 of them) → names, genres and casing are normalised → instructor names are resolved to identities → the classes are bulk-inserted → the run is marked success or partial (partial only if a core scraper failed — flaky studios don’t drag the whole run down) → permanent records reconcile → first-seen candidates are recorded → the revalidate webhook fires. Reconciliation and first-seen failures log warnings after run status is set, so scrape success alone does not prove either stage completed.

Turning “Coach Ana & Bea” into two people

A scraped instructor string is messy — honorifics, multiple names joined by & or x, “(Sub)” suffixes. The matcher splits it, strips titles, then tries in order: a studio-specific alias rule, an exact match to a known instructor, then a fuzzy match — but only auto-links a fuzzy match above 0.92 with a clear lead. Anything else is left unlinked and queued for a human to confirm.

Atomicity belongs around the whole batch

The action requires schedule access; the RPC independently locks an active studio and checks membership. It accepts 1–100 items dated today through today + 90 in Manila, inclusive. Each item calls the existing save_portal_class, retaining room/instructor, fee, confirmation and Studio Terms checks plus event creation. The new migration depends on the current class-pricing writer; frontend validation cannot replace that dependency.

The loop lives inside one PL/pgSQL exception block. Selected validation errors return ok: false, a zero-based index and a bounded error category; all earlier writes in that block roll back. Other errors propagate and abort the call rather than receiving a row-specific response. This follows PostgreSQL’s exception-block rollback semantics. Catching each item separately and continuing would change the product contract to partial success.

Atomic is not idempotent. The RPC creates fresh rows and has no batch retry key. If the response is lost after commit, blindly resubmitting can duplicate the batch; the sheet instead says to reload before retrying. After a confirmed save, public cache refresh, notifications and schedule reload run separately and may remain pending. A refresh-only failure is not permission to create the classes again.

A patch needs three meanings. An omitted field retains the existing edit; null removes that override and restores the source/default; an empty genre explicitly removes its tag. An empty instructor array means no teachers, while null inherits the scraped roster. The editor submits only changed fields. The server validates real calendar dates, bounded text, paired times and IDs as strings; converting a large database ID to a JavaScript number could lose precision. A note-only edit must not freeze all the other fields.

Authorization belongs at the write boundary. The action requires studio schedule access; the RPC independently checks a signed-in active member, an active studio still using scraped schedules, and a listed/cancelled record belonging to that studio. It locks the studio and record, allowlists patch keys, and validates a newly assigned room against that studio’s active rooms. A previously assigned room may remain after archival. Separate UPDATE/INSERT paths avoid an upsert’s insert guard rejecting an unchanged archived assignment. The migration retains existing RPC grants and table RLS; privileged helpers are not permission to trust a browser-supplied studio ID. See Supabase’s function-security guidance for execution privileges and a fixed search path.

Catch-up is field-specific and identity-aware. Re-scraping unchanged source preserves overrides. When source name, date, genre, time or instructor order catches up, normalization clears the redundant fields while retaining additions such as description, level, room and note. A declared date/name/time change extends reconciliation across the old date boundary; aliases still resolve to the original permanent key. Ambiguous declarations do not force unrelated records together, and the first-seen guard can hold the apparent new class as studio_edit. Undo removes all edits and returns to the latest source, not the snapshot from before editing; source cancellation remains cancellation.

Every downstream contract must follow the effective date. Save returns that date; undo returns the source date. If it falls outside the loaded 98-day window, the action reloads from the returned date so a successful move does not disappear from the editor. Takeover selects by effective date and copies edited details, preserving identity and external registration. The public view retains column names, order and types so existing readers can consume the projection.

Migration code also has dependencies. Apply the additive detail migration after schedule/calendar, scraped edits and takeover SQL. It patches installed view/function definitions and raises on unexpected shapes inside a transaction; textual patching still needs regression tests against the actual migration chain. Its verification query checks columns, privileges, RLS, view configuration and patched definitions. A frontend rollback keeps the additive schema and studio edits. A merged SQL file does not prove the database was upgraded, and a saved edit does not prove cache refresh succeeded.

Risks & gotchas

  • Scrapers are structurally fragile. Multiple studio booking systems, any of which can redesign, change a widget, or block a bot with no warning. There are partial defences — a studio returning zero classes is treated as an error, not a quiet week — but a format change that still parses can slip through and quietly publish wrong data.
  • Issue-based reporting still needs operational follow-through. The scrape-health workflow now maintains a labeled issue, but API failures, cancelled runs and unwatched notifications can leave findings unattended. Verify delivery and assign an owner; job success alone does not prove per-source freshness.
  • The security was once theatre. Row-level security was switched off on these tables while “public read” policies existed — so Postgres ignored the policies, and the underlying grants actually let the public key insert, update, and delete. Anyone loading the site could have wiped the data. Fixed by a hardening migration (RLS on, writes revoked, the rules table fully closed) — but it was live for a while.
  • Two frontends, one dataset. The website and shared mobile UI are separate codebases; native widgets add independent readers of the same tables; a feature built on the web (instructor pages) had to be ported to the app. The Barkhaus public/admin duplication tax, again.
  • Identity resolution needs a human. Unmatched instructor/studio pairs need a human decision in the CLI or new admin review queue. A UI reduces friction; it does not make a fuzzy guess authoritative.
  • Shared project, single environment. Same as MVL and Bonado: one Supabase project for three products, and the scraper writes straight to production — no staging.
  • Repo clutter. An earlier prototype (frontend/, data.json) still sits alongside the real web/ — harmless but confusing.

Data model — the shape

trips at the centre; users (registered or guest) join through memberships. Expenses are entries, each with rows for who paid (payers) and how it splits (shares, via line items). settlements record money actually moving between people. Every entry id is generated on the phone, not the server — so an expense created offline and synced twice lands once.

Key flows

Why writes go through a function — the concrete reason

Guest → real account

Tap an invite link and you’re in as a guest — a real but anonymous session, no sign-up. Data lab · preserve the currency of a debt and its payment

9b4e9cb, reviewed on remote main ce89c50, changes settlement accounting. Converting every balance into the trip currency too early loses which currency is actually owed. A later exchange-rate change can then make a supposedly cleared debt appear again. The new contract separates original debts, the actual payment and a display quote.

Source trail

docs/currency-settlements.md; src/lib/settlementMath.test.ts; scripts/test-currency-settlements.mjs + supabase/tests/currency_settlements.sql

Native balanceAmounts netted separately by original expense currency.New expenses, edits and settlement allocations.

For a synthetic debt of PHP 1,000 plus JPY 10,000, paying PHP 900 leaves PHP 100 plus JPY 10,000. At PHP 1 = JPY 3, a later JPY 10,300 payment clears both. Allocation first clears the payment currency, then other currencies in alphabetical order; excess becomes a credit in the payment currency. Opposing debts in different currencies remain visible even if their converted totals happen to cancel.

Client helpers round the combined quote once; SQL permits at most half a payment-currency cent of final conversion rounding. This is the app’s existing two-decimal model, not a general rule for every world currency. Missing required FX rejects the write rather than inventing a rate. Database settlement writes lock the trip, preserving a consistent allocation sequence. Metadata-only edits and later FX changes preserve allocations; deleting the settlement removes them. History/detail/export readers now carry payment currency too.

Risks & gotchas

  • High client complexity. A polished, app-feel SPA is a big surface: ~55 hooks and components, ~50 helper modules, plus native-shell and screen-transition machinery. It’s well-organised, but it’s a lot for one person to hold in their head.
  • The client-side data layer is hand-rolled, and a rewrite is deferred. Fetching and caching live across dozens of bespoke hooks; consolidating onto a standard library (TanStack Query) is explicitly parked as “fix it later.” The longer that waits, the more hooks there are to migrate.
  • Still one environment. Migrations are pushed to the linked project; the roadmap is full of “applied to production” notes. No staging — the same gap as Barkhaus and MVL.
  • Offline is create-only. New expenses queue offline; edits, deletes, and settlements need a connection. A deliberate scope cut, but a real limitation to communicate.
  • A lot is “code done, waiting on an account.” Apple sign-in, push (Firebase/APNs), crash reporting, universal links — all built, all gated on a person creating the external account and pasting a key. The app isn’t fully live until those are done.
  • Not isolated. Bonado, MVL, and Sansayaw all run inside one Supabase project (each in its own schema). A quota spike, an Auth-config change, or a bad migration has a three-product blast radius. Only Barkhaus has its own project.
  • Big roadmap, one maintainer. 15 phases and a deep TestFlight-feedback pass is impressive throughput, but it’s a large, growing surface relative to the team.

If we keep building it

  • Do the data-layer consolidation before the hooks multiply further. It’s the one piece of debt that compounds.
  • Add a staging project. Bonado has the tooling for it (migrations already run by CLI) — it just needs a second project to point at.
  • Treat it as the reference. Contracts (TypeScript + a schema types file), tested pure logic, CI, atomic writes, idempotent creates, dormant error tracking — this is the shape the Barkhaus retrospective asked for, already working. New projects should start from here.
