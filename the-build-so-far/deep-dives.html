The landscape

Fourteen folders sit in ~/Projects. They collapse into five groups — four real products and a bag of demos. Two folders are noise: mvl-vercel-upload.zip (a stale export) and Sponsor Logos/ (just image files).

The through-line: almost every product is a frontend served from a static host, talking to a Supabase backend for data, accounts and files, with a few outside services bolted on for payments, email and maps. Learn that one shape and you understand 80% of everything here. Only Barkhaus has a dedicated Supabase project; Sansayaw, MVL and Bonado share one.

A Barkhaus Live

In one line

A booking platform for a two-branch pet-care business (Estancia & Eastwood, at barkhaus.ph) covering daycare, overnight hotel, and grooming — with a staff admin console behind it. It is the most built-out project here and the only one taking real money from real customers.

Architecture

It follows the recurring pattern with one twist: two separate frontends share one Supabase backend. The public site is plain hand-written HTML and JavaScript (no framework, no build). The admin app is React and has to be compiled; the compiled result is committed into the repo and served alongside the site. Everything sensitive — payments, email, confirming a booking — runs in Supabase Edge Functions where the secret keys live.

Systems & why

SystemWhat it does hereWhy this choice / the trade-off
GitHub PagesServes the public site straight from the repoFree, nothing to run. But “no build” means no framework on the public side, and the React admin has to be pre-built and committed — which became the most fragile part of the pipeline.

Data model — the shape

bookings is the hub, but it does not hold the appointment date. That lives in a per-service detail table (grooming_details, hotel_details, …) as service_date. The booking_date column on the booking row is the date it was created — a naming trap that has broken the calendar, availability, and check-in code independently.

Key flows

A booking is born three ways

Online — the customer completes the wizard and pays on a hosted page; the payment webhook is what actually creates the confirmed booking and sends the email. Admin — staff use a 6-step panel; the submit-booking function writes it directly and emails immediately. Walk-in — staff mint a single-use token that opens the public wizard in a fee-free mode, also routed through submit-booking.

Risks & gotchas

  • Production is the only environment. Demo bookings, row-level-security changes, and webhook testing all run against live customer data. A staging project + seed script is the top item on the team’s own retrospective.
  • 37 database changes, applied by hand. Each schema change is a SQL file a person runs against the live database, then a cache-reload command. Forget the reload and the API throws phantom “relationship not found” errors. There is no automated migration runner.
  • The admin app is a built bundle committed to the repo — and a bot also commits it. This has raced a real fix and reverted it (“the regression that kept coming back”). The documented fix — build in CI, stop committing output — is agreed but not yet done.
  • Row-level security has failed silently. An insert-only policy let edits add new charge lines while deletes quietly failed → duplicated bills (real money data), caught only by a test’s totals check. Public availability had to move to narrow server-side functions because a normal query returned “no bookings” — making every slot look free — when the booking rows were private.
  • The same business logic lives in three places. Pricing and availability rules are re-implemented in the public site, the admin app, and the test suite, and they have drifted (hotel priced by pet size in one, by cage type in another).
  • Payment health needs an outside watchdog. A GitHub Action pings a health function every 20 minutes, because a silently-failing cron — or a Supabase usage cap that stops functions responding — would not otherwise be noticed.
  • The docs already disagree with the code. AGENTS.md and the technical doc still say “manual transfer is active, keep Maya off until launch” — but the live setting is 'maya' and card checkout is running. Documentation that isn’t updated with the change that invalidates it quietly turns into a trap.

If we rebuilt it

Mostly straight from the team’s own retrospective — the stack was judged right; the discipline around change is what it would upgrade.

  • Contracts first. Schema in migrations from commit one, generated types, one shared business-logic module every surface imports, and a one-page data dictionary that pins down date semantics.
  • Two environments. Production plus a staging Supabase with a seed script, so destructive testing never touches live data.
  • CI builds artifacts. Never commit build output; remove the bot’s write path entirely.
  • Loud failures from day one. No silent catch {}; error tracking (Sentry) on both frontends — which Bonado already does.
  • Keep what worked. Database-driven pricing, the idempotent-webhook + pending-hold + auto-cancel trio, single-use tokens, soft deletes, and the cached-token auth pattern all earned their place.

The four folders in this group

  • barkhaus — the live product described above.
  • barkhaus-dev — a companion workspace, not deployed: a self-contained test console (API assertions, paste-in E2E scripts, a 270-item manual checklist), the branded email template, and icon exports.
  • barkhaus-booking-staging — an active experiment rebuilding just the booking flow on a completely different stack (Cloudflare + a Next.js-like framework + a SQL toolkit), including “sign in with ChatGPT”. A bet on a cleaner foundation, not yet the real thing.
  • booking-platform — not code: a written kit for standing up a separate Barkhaus per client (own database, own deployment). Isolation by structure was chosen over one shared database with a “customer” column — see topic 9 in the reading list.

B MVL 2026 Live · seasonal

In one line

The event site for the Metarice Volleyball League’s 2026 invitational (metaricevolley.ph) — five game days across two weekends, Aug 29 to Sep 6. It captures player waivers, runs a game-day raffle, drives the livestream scoreboards, and collects award votes and post-event feedback. Built and re-tuned while the tournament was happening.

Architecture

A hand-written multi-page static site (17 pages, ~6,800 lines of plain JavaScript, no framework — a deliberate choice noted in the repo) on Vercel. The distinctive part is the backend: MVL does not have its own Supabase project. It lives in a dedicated mvl schema inside the Sansayaw project — and so does Bonado (its own bonado schema). Three of the four products, one Supabase project.

Every browser write goes through a public. database function (same “never trust the browser” rule as Barkhaus, taken further) — waivers, raffle check-ins, score entry, and scoreboard control are all server-side functions. The mvl.* tables are read-only to the public for league content; everything else is closed.

Systems & why

Data model — the shape

Everything sits in the mvl schema. games is the spine; teams, venues, and the two form tables (waiver_submissions, raffle_checkins) hang off it. The public can only read league content; every write goes through a function.

Key flows

The game-day raffle check-in — the signature flow

Two ways in: self (your own phone) or QR (a booth laptop where staff are signed in as admin). Either way the browser reads your location once — no manual pin — and hands it to one server function, which decides everything.

Live scoreboard

An admin creates a board and gets two links: a public read-only URL to drop into the livestream overlay (OBS), and a secret control URL a scorekeeper opens on a phone — no login — to tap points and sets. Updates are atomic server calls. Saving a set writes into game_sets, so the public schedule and standings update from the same record instantly. Court-side and big-screen views render the same board.

The phase flip

The site changes shape between “registration” and “game day” by editing one word in site-config.js. That swaps every page’s navigation (Rules/Waiver → Schedule/Videos/Teams/Rules/Check-In). The nav is one byte-identical block copied onto every page and stamped before the page paints, so wrong-phase links never flash. A one-line script checks that every page’s nav block is identical — the entire mechanism for “no page drifts out of sync.” Old URLs stay alive through a wall of redirects in vercel.json.

Risks & gotchas

  • The “one project per product” rule is broken here. MVL, Bonado, and Sansayaw all run inside one Supabase project (each in its own schema). Consequences: a redirect-list slip sends MVL’s admin login to Bonado’s site; Sansayaw’s daily scrapes and MVL’s game-day traffic share one quota; a migration mistake touches a database two other live products depend on. And this repo can’t use standard migration tooling — every schema change is run by hand against the live shared database.
  • The docs are badly out of date. HANDOFF.md still describes July: “raffle BUILT, pending one migration,” “remaining: team detail pages,” “phase deliberately not flipped.” Reality: the tournament ran, ~67 migrations landed, the phase is flipped, and there’s award voting, player check-ins, a raffle-draw system, a synchronized public draw display, and a feedback form. Same disease as the Barkhaus payment docs.
  • Two sources of truth for league data. js/league-data.js (teams, games, sponsors) was the original data source and is still used to render parts of the site, even though the same data lives in Supabase. The schedule page re-implements the standings ranking in JavaScript “until the page is wired to Supabase.” They can disagree.
  • Raffle rules changed ~10 times mid-event. Repeat winners, exclude-winner-dates, exclude teams, roster QR entries… the client re-decided eligibility game by game. This only worked because the logic was one server-side function to edit — a browser implementation would have needed a redeploy each time and drifted between the check-in page and the draw.
  • Scorekeeping by secret link. The scoreboard control URL is a bearer token — whoever has the link can score the match. Fine for a trusted volunteer on the day; it would need real accounts at any larger scale.
  • A hardcoded venue ID. The whole check-in flow depends on a magic UUID (11111111-…) pasted into the frontend. That venue row was once seeded with an empty location, which silently failed every check-in until a migration set the real coordinates.
  • Changes went straight to a production database during a live event. Raffle-rule migrations carried the note “get client go-ahead before applying — it’s their production DB.” There is no staging copy.

If we rebuilt it

  • Its own Supabase project. A free six-week event doesn’t justify entangling three products’ Auth, quota, and migration history. A new project costs nothing; unpicking this later is real work.
  • One data source. Once the pages read Supabase, retire league-data.js as a runtime source — keep it only as a seed file.
  • Keep the function-per-write discipline. It’s exactly what made the mid-event rule churn survivable. This is the pattern to carry forward, not fix.
  • Keep the one-word phase flip and the nav-sync check. Small, cheap, and it held up.
  • A staging copy. Same gap as Barkhaus — rule changes shouldn’t go straight to the live database mid-tournament.
  • Real accounts for scorekeepers if the event grows; the secret-link approach is an event-day expedient.

The sibling folders

  • mvl — the site described above (repo mvl-site).
  • mvl-admin-awards, mvl-raffle-repeat-winners, mvl-scoreboard-finish — not separate projects. They’re git worktrees: the same repository checked out to three different in-progress feature branches at once, so parallel work during the event crunch didn’t collide. A useful pattern to see — and a tidy-up job once the branches merge.

C Sansayaw Live

In one line

A directory of drop-in dance classes across Manila studios (sansayaw.org), plus an iOS app. Its defining trait: nobody types the data in. Every morning, robots read ~13 studios’ booking systems, clean up the results, and publish them.

Architecture

Three parts in one repository, one job each: a set of Python scrapers, a Next.js website, and a small iOS app. The scrapers run on a schedule and write to Supabase; the website and the app read from it. The seam between the two halves is a single “refresh your cache now” webhook.

Systems & why

SystemWhat it does hereWhy this choice / the trade-off
Python + PlaywrightThe scraping job: read ~13 studios’ booking systems (Wix, Mindbody, Shopify, widget APIs…), parse and cleanPython has the best ecosystem for “drive a browser, parse messy data, normalise it.” A real browser (Playwright) is only needed for 3 of 13; the rest read data endpoints directly. Deliberately the only Python in the portfolio.
GitHub Actions (cron)Runs the scraper every day at 6 AM Manila timeA free scheduled runner — no server to keep alive. Learned the hard way: a 30-minute timeout (a hung run once held a runner for 6 hours) and unbuffered logs (a killed job used to lose all its output).
SupabaseHolds studios, instructors, classes, and one row per scrape run — in the shared project’s sansayaw schemaThe scraper writes with the powerful service-role key; the site and app read with the public key, restricted to SELECT. Clean split of “who can change this” from “who can see it.”
Next.js + Vercel (ISR)Server-renders the site; fetches the whole dataset once into a cached functionEvery visitor gets the cached copy (fast, cheap), and the scraper’s webhook is what makes it refresh — so the site is never more than one scrape-cycle stale.
The revalidate webhookOne authenticated POST from the scraper that clears the site’s cache tagThe entire coupling between the two halves. Guarded by a shared secret; non-blocking — a failed call just means the site refreshes on its own timer instead.
Capacitor (iOS) + PostHogA small React app wrapped for the App Store, with a home-screen widget for today’s classes; product analyticsThe widget and native share need an app. It reads the same Supabase data — but it’s a separate codebase from the website, so features get ported between the two.

Data model — the shape

Four tables in the sansayaw schema. classes is the output; each row is tagged with the scrape_run that produced it, the studio it’s at, and (if resolved) an instructor. A private rules table, instructor_aliases, is what turns a scraped name into a real identity.

Key flows

The daily pipeline

The cron fires → the scraper opens a run record → each studio scraper pulls its data (a real browser for only 3 of them) → names, genres and casing are normalised → instructor names are resolved to identities → the classes are bulk-inserted → the run is marked success or partial (partial only if a core scraper failed — flaky studios don’t drag the whole run down) → the revalidate webhook fires. About seven minutes end to end.

Turning “Coach Ana & Bea” into two people

A scraped instructor string is messy — honorifics, multiple names joined by & or x, “(Sub)” suffixes. The matcher splits it, strips titles, then tries in order: a studio-specific alias rule, an exact match to a known instructor, then a fuzzy match — but only auto-links a fuzzy match above 0.92 with a clear lead. Anything else is left unlinked and queued for a human to confirm.

Risks & gotchas

  • Scrapers are structurally fragile. ~13 different studio booking systems, any of which can redesign, change a widget, or block a bot with no warning. There are partial defences — a studio returning zero classes is treated as an error, not a quiet week — but a format change that still parses can slip through and quietly publish wrong data.
  • Failures are visible only in a log. A partial run, or a studio dropping to zero, shows up in the GitHub Actions output — nothing pages anyone. For a data product whose whole value is freshness and accuracy, that’s the biggest gap.
  • The security was once theatre. Row-level security was switched off on these tables while “public read” policies existed — so Postgres ignored the policies, and the underlying grants actually let the public key insert, update, and delete. Anyone loading the site could have wiped the data. Fixed by a hardening migration (RLS on, writes revoked, the rules table fully closed) — but it was live for a while.
  • Two frontends, one dataset. The website and the iOS app are separate codebases reading the same tables; a feature built on the web (instructor pages) had to be ported to the app. The Barkhaus public/admin duplication tax, again.
  • Identity resolution needs a human. Unmatched instructor/studio pairs sit unlinked until someone runs the review CLI — low-tech and correct, but a standing chore.
  • Shared project, single environment. Same as MVL and Bonado: one Supabase project for three products, and the scraper writes straight to production — no staging.
  • Repo clutter. An earlier prototype (frontend/, data.json) still sits alongside the real web/ — harmless but confusing.

If we keep building it

  • Alert on scrape health. A partial run or a studio at zero should send a message, not just sit in a log. Highest-value addition for a scraper product.
  • Per-scraper “expected shape” checks. Assert each studio returns a plausible count and structure, so a silent format drift becomes a loud failure.
  • Decide the two-frontend question. Either share one codebase, or keep them separate on purpose and factor the shared data/render logic into a package.
  • Keep: the service-role-writes / public-reads split, the pure tested matcher, the webhook seam, and treating “0 classes” as an error.

D Bonado In build · on TestFlight

In one line

A mobile-first app for splitting shared trip expenses with friends — add expenses, see who owes whom, settle up. Same core stack as the others, but built deliberately: it is roughly the “if we rebuilt it” list from Barkhaus, executed. 15 build phases, ~47 database migrations, automated tests + CI, shipped to iOS TestFlight.

Architecture

A React single-page app (Vite + TypeScript + Tailwind, also an offline-capable PWA) on Vercel, wrapped for iOS with Capacitor. The backend is Supabase, in its own bonado schema. What sets it apart isn’t the pieces — it’s the discipline around them: typed code, tested money math, proper migration tooling, error tracking wired in, and nearly every write routed through an all-or-nothing database function.

Systems & why

Data model — the shape

trips at the centre; users (registered or guest) join through memberships. Expenses are entries, each with rows for who paid (payers) and how it splits (shares, via line items). settlements record money actually moving between people. Every entry id is generated on the phone, not the server — so an expense created offline and synced twice lands once.

Key flows

Why writes go through a function — the concrete reason

Guest → real account

Tap an invite link and you’re in as a guest — a real but anonymous session, no sign-up. Your expenses attach to a users row flagged “not registered.” Later, “claim your account” links a Google or Apple identity onto that same row — nothing is copied or lost, the row just gains a real identity. If you never claim it, you stay a working guest.

Native sign-in done properly

Inside the iOS app, Google sign-in opens the system browser, not an in-app web view (Google blocks OAuth in embedded views), returns through a bonado:// link the app catches, and the session is stored in app-scoped storage rather than the web view’s evictable storage. Small details, but they’re the difference between “sign-in works” and “sign-in randomly fails.”

  pendingEntryId.current ??= crypto.randomUUID()
  return pendingEntryId.current
}

// A retry reuses p_entry_id; the database returns the existing expense.
p_entry_id: claimEntryId()
Predict

The server commits an expense but the response disappears. What happens when the phone retries with the same ID? What if it generates a new ID?

Risks & gotchas

  • High client complexity. A polished, app-feel SPA is a big surface: ~55 hooks and components, ~50 helper modules, plus native-shell and screen-transition machinery. It’s well-organised, but it’s a lot for one person to hold in their head.
  • The client-side data layer is hand-rolled, and a rewrite is deferred. Fetching and caching live across dozens of bespoke hooks; consolidating onto a standard library (TanStack Query) is explicitly parked as “fix it later.” The longer that waits, the more hooks there are to migrate.
  • Still one environment. Migrations are pushed to the linked project; the roadmap is full of “applied to production” notes. No staging — the same gap as Barkhaus and MVL.
  • Offline is create-only. New expenses queue offline; edits, deletes, and settlements need a connection. A deliberate scope cut, but a real limitation to communicate.
  • A lot is “code done, waiting on an account.” Apple sign-in, push (Firebase/APNs), crash reporting, universal links — all built, all gated on a person creating the external account and pasting a key. The app isn’t fully live until those are done.
  • Not isolated. Bonado, MVL, and Sansayaw all run inside one Supabase project (each in its own schema). A quota spike, an Auth-config change, or a bad migration has a three-product blast radius. Only Barkhaus has its own project.
  • Big roadmap, one maintainer. 15 phases and a deep TestFlight-feedback pass is impressive throughput, but it’s a large, growing surface relative to the team.

If we keep building it

  • Do the data-layer consolidation before the hooks multiply further. It’s the one piece of debt that compounds.
  • Add a staging project. Bonado has the tooling for it (migrations already run by CLI) — it just needs a second project to point at.
  • Treat it as the reference. Contracts (TypeScript + a schema types file), tested pure logic, CI, atomic writes, idempotent creates, dormant error tracking — this is the shape the Barkhaus retrospective asked for, already working. New projects should start from here.
