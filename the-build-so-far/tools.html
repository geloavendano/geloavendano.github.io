The design toolkit

Reference, not curriculum. Start with the user journey and information hierarchy in the build playbook. Return here when a concrete interface problem needs a pattern.

In one line

Everything else in this handbook documents what was already built. This page is the opposite: a catalog of how the next screen could look and move, ready to be picked from before it’s designed.

What it actually is

Not a mood board. Every entry below is a working implementation, not a picture of one: the neumorphism button really is built in neumorphism, and the masonry layout really is CSS columns. There are five catalogs, each with a letter code, meant to be used in build order:

Why the shorthand matters here

A code like C-42 or S-17 is short enough to type straight into a prompt. “Build the dashboard using F-01 colour roles, an L-03 bento layout, and C-42 stat cards, skinned in S-17 dark mode” gives an agent a precise spec instead of a vague description. It’s the same instinct as the inspectable prompt in Part IV, aimed at how things look instead of how they work.

What it isn’t

  • Not a brand system. It catalogs how things can look and move. A real project still needs its own colours, type and voice decided on top.
  • Not wired into any project yet. No repo’s CLAUDE.md or skills point at it. Worth one line in each project’s briefing: “check the design toolkit in the handbook before building a new screen.”

How it looks here

The catalog started as a standalone file, ux-design-kit-gelo/ux-field-kit.html, and now lives on this page. It uses the handbook’s type and colours for its labels, and the specimens keep their original light backgrounds even in dark mode, so each one still shows its style accurately. Every catalog code is unchanged.

R

Quick-start recipe

  1. Set Foundations (F) — color roles, type scale, spacing, shape, elevation, states, and accessibility.
  2. Pick a Visual Style (S) — or blend two, e.g. S-10 minimalism over S-16 aurora backgrounds.
  3. Choose a Layout (L) per screen type — landing → L-11, app → L-08, dashboard → L-03 or L-02.
  4. Layer Motion & Scroll (M) only when it clarifies flow, depth, feedback, or screen transitions.
  5. Assemble Components (C) onto the layout, greyscale first. Structure and flow before beauty.
  6. Apply the style to promote the wireframe into a mockup.
// Example screen spec, in catalog shorthand:
"Analytics dashboard" = F-01 semantic color + F-03 spacing → L-08 shell → L-03 bento content →
C-42 stat cards + C-43 chart + C-28 table → M-04 hover feedback, skinned in S-17 dark mode.

Design libraries

Everything in the catalog above is plain HTML and CSS: cheap, fast, and it works everywhere. These four go a step further, into real-time graphics drawn by the graphics chip (WebGL): shaders, true refraction, 3D. They’re for the one moment on a page that should feel alive, not for every screen.

Three rules before using any of them

  • One per page, at most. Each keeps the graphics chip busy every frame. A moving gradient behind a glass nav bar behind a 3D hero drains a phone’s battery and stutters on older laptops.
  • Always ship the still version. Respect the “reduce motion” setting (every sample here stops animating when it’s on) and keep a fallback for devices without WebGL. The CSS entries in the catalog, S-05 Liquid Glass and S-16 Aurora, are exactly that fallback.
  • Decoration can’t carry meaning. Nothing a person needs to read or press should depend on the effect rendering.

In a prompt, name the catalog entry and the library: “an S-16 aurora hero, rendered with ShaderGradient, with the CSS version as the reduced-motion fallback.”

ShaderGradient

github.com/ruucm/shadergradient ★ 2.5kMITupdated Sep 2026

A 3D surface — a flat plane, a sphere, or a rippling water plane — painted with a three-colour gradient and slowly deformed with noise. Designers tune it by eye at shadergradient.co, then paste the settings into code, either as props or as one URL string.

Reach for it when

A hero or section background needs to feel alive and premium: a launch page, a login or splash screen, a brand page. It’s the grown-up version of S-16 Aurora.

The catch

In code it’s React-only, and it brings the whole of three.js — the heaviest download on this page. Versions have to match: its README carries a compatibility table (React 19 with react-three-fiber 9 for Next.js 15). The sample above hit exactly this problem: the CDN served two copies of React until the page forced them into one. In a normal project the package manager sorts it out. And the npm package says MIT, but the GitHub repo has no licence file — fine to use, worth knowing.

In a real project

terminal, then any React component

npm i @shadergradient/react @react-three/fiber three three-stdlib camera-controls

import { ShaderGradientCanvas, ShaderGradient } from '@shadergradient/react'

<ShaderGradientCanvas style={{ position: 'absolute', inset: 0 }}>
  <ShaderGradient type="plane" color1="#3a55c8" color2="#8fa2ff" color3="#f6f5f1"
    uSpeed={0.3} uStrength={4} lightType="3d" />
</ShaderGradientCanvas>

Liquid metal · liquid-logo

github.com/paper-design/liquid-logo engine: paper-design/shaders ★ 1.1k app · 3.5k engineApache-2.0 engine

liquid-logo is Paper’s small web app (liquid.paper.design): upload a logo and get it back as flowing liquid chrome. It isn’t something you install — the engine underneath is. That engine is Paper Shaders, an open-source set of about 30 GPU effects. LiquidMetal is one of them, and it’s what the sample runs, fed with the handbook’s own three-bar mark.

Reach for it when

There’s a brand moment: a hero logo, a splash or loading screen, a launch page. The rest of Paper Shaders — mesh gradients, grain, dithering, water — covers much of ShaderGradient’s ground without three.js, at a third of the weight.

The catch

Two different licences. The liquid-logo app’s code is under PolyForm Shield: you can read it, but not use it to build a competing product, so don’t copy from that repo. The Paper Shaders package is Apache-2.0 and safe to ship. The logo has to be a flat, single-colour shape on transparency; detailed marks turn to mush. And it’s pre-1.0 (version 0.0.81), so expect breaking changes and pin the version.

In a real project

terminal, then any React component

npm i @paper-design/shaders-react

import { LiquidMetal } from '@paper-design/shaders-react'

<LiquidMetal image="/logo.svg" colorBack="#e9e7e1" colorTint="#8fa2ff"
  repetition={4} softness={0.45} distortion={0.1} speed={1}
  style={{ width: 320, height: 320 }} />

liquid-glass-js

github.com/dashersw/liquid-glass-js ★ 1.0kMITupdated Jun 2025

Glass buttons and bars that really refract what’s behind them — the look of Apple’s Liquid Glass — in plain JavaScript. It photographs the page once (with a helper called html2canvas), then a WebGL shader bends that photo through each glass shape: the edges magnify and the rim catches the light.

Reach for it when

A floating toolbar, tab bar or set of media controls sits over a rich, mostly still background — a photo, a gradient. It’s the real version of S-05 Liquid Glass, which only fakes it with blur.

The catch

  • The photo is taken once. If what’s behind the glass changes — a scrolling feed, video, animation — the glass shows a stale picture. That’s why the sample runs in its own small frame instead of on this page.
  • It’s a personal project. It isn’t on npm (the npm package with the same name is someone else’s), was last updated in June 2025, and has no tests. Copy its two files into your project, as this handbook does in samples/vendor/, rather than depending on it.
  • The glass is a picture. Text on it can’t be selected, and contrast has to be checked by eye.

react-three-fiber

github.com/pmndrs/react-three-fiber ★ 32kMITupdated Sep 2026

Not an effect — a foundation. three.js is the standard way to draw 3D in a browser; react-three-fiber lets you write a 3D scene the way you write React screens: a shape is a component, a click is an onClick, state is useState. ShaderGradient is itself built on it.

Reach for it when

The 3D is the feature: a product you can turn around, a room or venue map you can explore, a data sculpture, an interactive hero.

The catch

3D is its own craft — cameras, lights, materials, frame budgets — so budget learning time or keep scenes simple. The download is heavy, and the helper packages most projects add (drei, post-processing) grow it further. Phone graphics chips vary widely: test on a mid-range Android, not only an iPhone. Anything interactive needs a keyboard and screen-reader alternative, because a canvas is invisible to both.

Where each one fits in a build

Too many design skills pulling in different directions is a real risk. UI UX Pro Max and Emil’s skills sometimes disagree on taste. When they do, your own words and the project’s existing design win, then the catalog codes you picked.

UI UX Pro Max

github.com/nextlevelbuilder/ui-ux-pro-max-skill ★ 129kMITupdated Sep 2026

A local design database with a search tool that Claude runs by itself. Ask for a product and it returns a whole starting direction: page pattern, visual style, colour roles, font pair, effects, what to avoid, and a pre-launch checklist. Everything runs on your Mac with a small Python script; nothing is sent anywhere.

The catch

  • Its picks are a starting point, not a decision. Asked for a friendly pet-booking service, it suggested claymorphism in teal. That’s plausible, and also what many other sites get. Compare it with the catalog above before committing.
  • The logo and icon tools use paid AI image services. The design skill generates logos with Google’s Gemini and similar services, which need an API key and cost money per image. Set keys up yourself; never paste one into chat.
  • It’s built as a plugin but installed here as plain skills. (The desktop app doesn’t have Claude Code’s plugin command.) Its instructions point at a plugin folder, but the search script lives in ~/.claude/skills/ui-ux-pro-max/scripts/. Claude finds it there; it was tested at install.

visual-plan

github.com/BuilderIO/skills · visual-plan ★ 4.3kMITlocal-files mode

Normally Claude writes its plan as a long message in chat. visual-plan replaces that with a review page: wireframes of every screen, a clickable prototype where interaction matters, the real files it will touch, and a list of open questions for you to answer. Ask it for a flow or journey and it draws one wireframe per screen, with arrows between the steps. That makes it the tool for reviewing user flows before anything is built.

Reviewing a user flow, step by step

  1. Open Claude Code in the project whose flow you want to review, for example ~/Projects/barkhaus.
  2. Ask for the flow by name, and say which screens start and end it (example below).
  3. Claude writes the plan into a plans/ folder in that project, checks it, and opens it in your browser. Use Chrome: Safari can block the page from reading the plan on your Mac.
  4. React in chat (“merge steps 2 and 3”, “what happens if the payment fails?”). Claude edits the plan and refreshes it.
  5. Approve it. Only then does Claude start changing code.

in Claude Code, inside the project

/visual-plan Storyboard the Barkhaus booking flow as it works today, from
choosing a service to the payment confirmation email. One wireframe per
screen, and mark every place a customer could get stuck.

What “local files” means here

  • Your plans stay on your Mac. They’re plain files in the project, so they can be committed to git like any other document. Nothing goes to BuilderIO’s database, and no account is needed.
  • The viewer is still their web page. The browser tab opens BuilderIO’s plan viewer, which reads the files straight from your machine. They keep basic page-view and error counts for that page, but not the plan itself.
  • No links, no comments. Only you can open it, on this Mac. If you later want to share plans with a client and collect comments, switching to the hosted mode takes one command plus a sign-in you do yourself; the plans are then stored on BuilderIO’s servers.

The catch

It’s eager: its instructions tell Claude a plan is worth making for fairly small UI changes too. For a quick tweak, say “no plan needed”. The review page also needs an internet connection, because the viewer is hosted even when the plan files are local.
