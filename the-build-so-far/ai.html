The working loop: stay the architect

Vibecoding becomes risky when a plausible output substitutes for understanding. The remedy is not to type every line yourself; it is to control the decisions and demand evidence. Give the agent a well-shaped job, let it do the mechanical work, then reconstruct the system in your own words.

1Frameobjective, context, constraints, done
2Inspectexisting code and conventions
3Decidearchitecture and trust boundary
4Changesmall, reviewable slice
5Verifytests plus runtime evidence
6Explainteach it back and record why

A prompt that makes the work inspectable

Four parts · enough structure for most feature work

Objective: Add [small user outcome].
Context: The relevant flow starts in [files/feature]. [Rule] owns the decision.
Constraints: Preserve [behaviour]. Never trust [browser input]. Do not change [scope].
Done when: [observable behaviour], [tests], [live/runtime evidence], and explain the request path.

This follows the same shape OpenAI recommends for coding-agent prompts: identify the goal, include the context and constraints, and make the completion criteria testable. The prompt is a compact specification, not a substitute for inspecting the repository.

The seven questions to ask before accepting a change

  1. What user-visible state changed?

    Name the event that starts it and the evidence the user sees when it succeeds or fails.

  2. Can I trace it end to end?

    Event handler → rule → request → trusted boundary → database or dependency → response → rendered state.

  3. Where does the important rule live?

    If the answer is “in several nearly identical places,” the change has created future disagreement.

  4. What input is untrusted?

    Prices, permissions, identity claims, results, and idempotency must be checked at an authoritative boundary.

  5. Which failure did we prove?

    A happy-path test is not evidence that denial, retry, duplication, or dependency failure behaves safely.

  6. What does the diff not prove?

    Build output, network behaviour, policies, migrations, and deployment configuration need runtime evidence.

  7. Can I explain it without the agent?

    Complete a Feature X-ray. Any blank is the next thing to inspect.

The useful distinction

A feature name tells you where to configure something today. The durable need tells you why it exists and how to reproduce the practice in another tool tomorrow.

Working with AI, day to day

In one line

Most of this portfolio is built through Claude Code, not despite it. Two habits make that work in practice: a clear line between what an agent may do alone and what a human executes, and a record of what was learned so the next chat doesn’t relearn it. The sections that follow — Briefing Claude, Skills, MCP, Scheduled runs, Hooks, Subagents — are the tools. This is the ground rules they all sit on.

The human/AI boundary — the Supabase rule

Barkhaus states it outright, and every project with a database follows the same shape in practice: an agent may draft anything — code, SQL migrations, RLS policy changes, edge-function updates — but a human executes anything that touches the live database or a deploy a customer will hit.

Coordinating without a review process

None of these repos run the branch-plus-pull-request process a larger team would — every deep-dive notes the same “single maintainer” pattern. Barkhaus’s AGENTS.md sets a lighter convention instead: claim what you’re about to work on in a shared .agents/BOARD.md file, prefer a separate branch or worktree for concurrent work, and leave a short handoff note when you stop — the Board check hook later on reads that same file back at the start of each chat. MVL shows the idea at its most literal: mvl-admin-awards, mvl-raffle-repeat-winners and mvl-scoreboard-finish are git worktrees — the same repo checked out to three codex/* branches (OpenAI’s coding agent) at once, so parallel AI-driven feature work didn’t collide during the tournament crunch.

Commits carry attribution

An AI-authored commit ends with a co-author line, the same way a human co-author would be credited. It’s in Barkhaus’s real history — the server-side pricing fix (see the Barkhaus deep-dive) was committed as:

Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>

Small detail, real payoff: months later, git log still shows who — or what — wrote a line and why. The commit message is the explanation, not just the diff.

What the retrospective actually taught

  • A good bug report is most of the fix. Barkhaus’s own retrospective: open reports with the exact error text, the network request and response, and the schema of the table involved — every fast fix in that project’s history started that way.
  • “Audit everything in this area” beats one symptom at a time. One such request in Barkhaus surfaced and fixed six latent bugs in a single pass, instead of six separate rounds.
  • Incidents become institutional memory, not folklore. Barkhaus appends every root cause to a gotchas table in its own docs (technical-doc.html §12) — the next session, human or AI, reads it instead of rediscovering the bug.
  • None of this replaces judgment on what can’t be undone. The Supabase boundary above exists because an agent is a fast, tireless drafter — not the party accountable when a migration goes wrong on a live, shared database.

Claude Code adapter: CLAUDE.md

Same concept in Codex: use AGENTS.md. The syntax and discovery rules differ, but the content should answer the same questions: what this project is, how to verify it, where the boundaries are, and what must not be guessed.

Every Claude Code chat starts with no memory of the last one. Without a briefing, it relearns each project by reading the code, which costs tokens every time and still misses what the code doesn’t show: that booking_date is the day a booking was created, or that supabase db push from the MVL repo would touch Sansayaw’s migration history. A CLAUDE.md file is that briefing. Claude reads it at the start of every chat in the folder.

Why it earns its place

  • The traps in this handbook are invisible in the code. Almost every item under “Risks & gotchas” above is something a careful reader of the repo would still get wrong. Written down once, Claude avoids them in every chat.
  • It replaces re-exploration. Commands, where things live, and which database a repo writes to take several file reads to rediscover. A few lines answer them for free.
  • It’s where boundaries live. “Draft migrations, but I apply them” is a decision only you can make, and without a written rule Claude has to guess or ask each time.
  • It isn’t free. The whole file is sent with every message, so every line is paid for repeatedly. Aim for roughly 30–150 lines, and point to longer docs instead of copying them in.

Three excerpts

Most lines tell Claude what not to do. That’s deliberate: it can read what exists, but not which obvious-looking fix would break something.

bonado/CLAUDE.md · Rules that are easy to break

- **Multi-row writes go through a SECURITY DEFINER function (RPC), never plain inserts.**
- **Entry ids are generated on the device** so a retried or offline-synced submit lands once.
- **Expenses store the exchange rate as of their date.** Never recompute with today's rate.

mvl/CLAUDE.md · Commands

- Apply one migration: `supabase db query --linked --file supabase/migrations/<file>.sql` (**never `db push`**)
- Nav check after touching any nav — must print `1` (see `HANDOFF.md`, "Standing invariant")

dance-scraper/CLAUDE.md · Boundaries

- Don't run `python run.py` against production to test a change; test one scraper's parse step instead.
- `.env` holds the service-role key. Never print it, commit it, or pass it to `web/` or `mobile/`.

What stays out

  • Anything the code already says. Folder trees, dependency lists, how React works.
  • Long explanations. Link to HANDOFF.md or the technical doc instead; every line is resent with every message.
  • Secrets. The file is committed. Name where the key lives, never the key.
  • Generic advice. “Write clean, tested code” changes nothing.

Keeping it true

  • Claude doesn’t update it on its own. When it trips on something in a chat, say “add that to CLAUDE.md” before you close the chat. Or do what Barkhaus does and write that instruction into the file itself.
  • Start new projects with /init, which scans the repo and writes a first draft. Then trim it and reshape it to the outline above.
  • A wrong briefing is worse than none. Barkhaus’s AGENTS.md and MVL’s HANDOFF.md have both drifted from the code, and Claude trusts what it’s told. Update the file in the same commit as the change that makes it wrong.

Skills: repeatable procedures

A CLAUDE.md holds facts that matter in every chat. A skill holds a procedure you only need sometimes: how to work through a round of test feedback, or how to prepare a database change you’ll run by hand. Each skill is a folder containing a SKILL.md file.

MCP: giving Claude access

CLAUDE.md tells Claude the rules and a skill tells it how to do a task. MCP (Model Context Protocol) gives it access: a standard way to connect Claude to a database, a hosting dashboard, or an analytics account. Each connection is an MCP server, and each server offers a set of tools, such as “list tables” or “get deployment”, that Claude can call when a task needs them.

You already use MCP without knowing it: the built-in browser, Chrome control, scheduled tasks and the terminal panel in the desktop app are all MCP servers the app provides. None are connected to your own services yet.

Three ways Claude reaches things

Why it matters here

About 30 of your past prompts were you pasting data in by hand: table rows ([{"idx":0,"id":…), column lists, RLS policy dumps, “here’s my schema”, “below is the existing edge function”. Every one was a round trip where Claude couldn’t look for itself, and the pasted copy could already be out of date. A read-only Supabase connection removes those round trips. A Vercel connection does the same for “is it live?” and NOT_FOUND after a redeploy.

What to connect

ServerUse it forSet it up asVerdict
SupabaseSchemas, RLS policies, rows and function logs, read directlyRead-only, one connection per project: Barkhaus, and the shared sansayaw projectConnect first
VercelDeployment status and build logs for MVL, Bonado and the Sansayaw siteAs is: its tools only list and inspectConnect
SentryCrash reports with stack tracesAfter switching on Sentry in Bonado, where it’s built but inactiveLater

GitHubPRs, issues, CI runs—Skip: gh does it

Resend’s server has about 85 tools, including sending broadcasts and creating API keys. Keep outgoing email a deliberate, manual action.

Rules for connecting anything

  • Read-only for anything in production. Write access to a live database through a connection is the same as handing over the admin password. CLAUDE.md can ask Claude not to apply migrations; a read-only connection makes it impossible.
  • One project per connection. Barkhaus’s connection shouldn’t be able to reach the shared project that holds MVL, Bonado and Sansayaw, and the reverse. Shared blast radius is already this portfolio’s biggest structural risk; don’t extend it to Claude’s access.
  • What comes back is data, not instructions. A table row, a log line or an email body can contain text that looks like a command. Claude treats it as content, and so should you when reviewing what it did.
  • Connect what you’ll use. Each server adds tools Claude has to choose between. The app loads tool details only when needed, but ten idle connections still add noise and more to review.

Setting it up

  • In the desktop app: add a connector from Claude’s settings. Sign-in happens on the service’s own page, and you do it yourself.
  • For one repo: a .mcp.json file in the repo root lists that repo’s servers and is committed with the code. It’s the cleanest way to give each repo only its own Supabase project.

mvl/.mcp.json · a sketch; check Supabase’s MCP docs for the current options

{

    "supabase": {
      "type": "http",
      "url": "https://mcp.supabase.com/mcp?project_ref=<sansayaw-project-ref>&read_only=true"
    }
  }
}

The project ref appears in each repo’s Supabase URL (MVL records it in backend/README.md). Barkhaus’s file points at Barkhaus’s project. Bonado, MVL and dance-scraper each point at sansayaw, and each repo’s CLAUDE.md says which schema is its own.

Rules for unattended runs

  • Every run starts from nothing. It remembers no chat, so the prompt must say exactly what to check, where, and how to report. It does read each repo’s CLAUDE.md and your skills, which is why those came first.
  • Report, don’t act. With nobody watching, a run reads, checks and writes a report, or at most opens a PR or a draft. It never deploys, applies migrations or sends email. These are the same boundaries as in the CLAUDE.md files, and they matter more here.
  • Define “nothing to report”. A run that says “all fine” in three paragraphs every week gets ignored. Ask for one line when nothing needs attention.
  • Content isn’t instructions. A run reading scraped pages or issue comments on its own can meet text that tries to redirect it. Report-only runs limit what that could do.
  • Weekly is usually enough. Every Claude run uses your limits. Put anything that needs to run often into a script.

Hooks: rules that enforce themselves

A hook is a shell command Claude Code runs automatically at a set moment: before a tool runs, after a file is edited, when Claude is about to finish a reply, when a chat starts. Claude doesn’t decide to run it; the app runs it every time. That makes hooks the only piece here that doesn’t depend on Claude remembering something.

CLAUDE.mdSkillMCPHook
DoesStates the rulesDescribes a procedureGives accessEnforces or automates
Relies onClaude following itThe description matchingWhat’s connectedNothing: the app runs it
MVL example“Never db push”supabase-changeRead-only Supabasedb push is refused

Where hooks sit in a single turn

The events that matter here

EventFiresWhat a hook can do
PreToolUseBefore a tool runs, e.g. a shell command or a file editBlock it, and tell Claude why and what to do instead
PostToolUseAfter a tool succeedsIt can’t undo the action, but it can hand Claude a problem to fix
StopWhen Claude is about to finish its replySend Claude back to keep working
SessionStartWhen a chat starts or resumesAnything it prints becomes context Claude sees
NotificationWhen Claude needs your attentionNothing for Claude, but it can alert you, e.g. with a Mac notification

Claude Code passes the hook a description of what’s happening, including tool_name, tool_input.command and tool_input.file_path. The hook answers with its exit code: 0 means carry on, 2 means block, and whatever it printed to stderr goes back to Claude as the reason. Hooks live in the same settings files as permissions: ~/.claude/settings.json for all projects, .claude/settings.json in a repo (committed), or .claude/settings.local.json (just you).

One hook, in full

mvl/.claude/settings.json

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard.sh" }] }
    ]
  }
}

mvl/.claude/hooks/guard.sh

#!/bin/bash
# Refuse commands that touch the shared production project
cmd=$(jq -r '.tool_input.command')
if [[ "$cmd" == *"supabase db push"* ]]; then
  echo "Blocked: never db push from MVL. The migration history belongs to Sansayaw.
Use: supabase db query --linked --file <migration>" >&2
  exit 2
fi
exit 0

Claude reads the refusal, sees the right command, and changes course. The message is written as an instruction, not just a “no”, because Claude acts on it.

Things to know

  • Hooks run with your permissions, automatically. A hook in a repo runs on your Mac as you, which is why project hooks only run once you’ve trusted the folder. Read the hooks in any repo you didn’t write.
  • Keep them fast. A PostToolUse hook runs after every matching edit. The Bonado build-lint-test run belongs in Stop (once per reply), not after each edit.
  • A guard is a safety net, not a wall. A text match catches supabase db push, but the same result can be reached another way. Guards catch honest mistakes. Read-only credentials (see MCP) are the real protection for production.
  • Keep the rule in CLAUDE.md too. The written rule explains why, so Claude plans around it and rarely hits the guard. The hook is there for the time it forgets.

Subagents: delegating to a separate worker

A subagent is a separate Claude worker the main chat sends off on one task. It gets its own context, the working memory of everything read so far, does the work there, and hands back only a summary. None of the files it opened or searches it ran end up in your main chat.

When it pays off, and when it doesn’t

GainCost
Main chat stays clean. 40 file reads become one paragraph, so every later message in the chat is smaller and cheaper.Starts from nothing. It doesn’t know what the main chat knows; the instruction has to carry the context, or it re-reads.
Parallel. Several workers search at once.More tokens in total. The main chat shrinks, but the overall work grows. A worker for a two-file lookup is waste.
Cheaper model. Searching doesn’t need Opus; Haiku or Sonnet will do.Summaries lose detail. Fine for “where is X”; risky for “is this safe”.
Limited tools. A reviewer that can read but not edit.No back-and-forth. It works from one instruction and can’t ask you anything mid-task.
Fresh eyes. It doesn’t share the assumptions of the chat that wrote the fix.

Use a subagent when the reading is big and the answer is small. In this portfolio that means searching across a surface, reviewing before something is applied, or verifying after a fix.

Built-in and your own

  • Built in. Explore (read-only, fast searching), Plan (designs an implementation without editing), general-purpose (can do anything the main chat can), and claude-code-guide (answers questions about Claude Code).
  • Your own. A Markdown file in ~/.claude/agents/ for all projects, or <repo>/.claude/agents/ for one. Like a skill, its description decides when it’s used. Unlike a skill, it runs separately with the tools and model you give it.
  • Asking for one. Claude doesn’t always delegate on its own. Saying “use subagents to search each surface in parallel” is enough.
